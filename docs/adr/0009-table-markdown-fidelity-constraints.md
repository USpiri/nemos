# ADR 0009 — Markdown-Fidelity Constraints for Tables

**Date:** 2026-08-13
**Status:** Accepted

## Context

Notes have no database behind them — a Note's Markdown file *is* the data. Anything the table editor can represent but Markdown cannot is data a user can permanently lose just by opening and re-saving a Note. Every Table this editor can produce is therefore held to a fixed set of GFM-representable constraints: exactly one **mandatory header row** (row 0 is always `tableHeader` cells — a structural invariant `@tiptap/extension-table`'s `parseMarkdown` already establishes when parsing `token.header` into row 0, ahead of any of the header-row *editing* guarantees — undeletable, unreorderable — layered on top of it by later tickets); alignment that exists only **at the column level**, never per cell; cell content that is **inline-only** (GFM table cells are one line of inline Markdown, nothing block-level); and **no cell merging, no column resizing, no per-cell color** — none of the three has any GFM syntax to round-trip through, so none is offered, now or later.

The existing `src/components/editor/extensions/table` implementation already builds on `@tiptap/extension-table`, and empirical verification (constructing the app's real `Editor` with a sample GFM table and inspecting `getJSON()`/`getMarkdown()`) confirmed the base package's tokenizing/parsing, Markdown serialization, and row/column commands (`insertTable`, `addRowBefore/After`, `addColumnBefore/After`, `deleteRow`/`deleteColumn`, `mergeCells`/`splitCell`) all already work correctly, including the header-row invariant. The verified, narrower gap against the constraints above: **Column Alignment** is parsed by `marked.js` into a per-column `align` array and then silently discarded — never stamped onto any node attribute, never re-emitted on save; the cell content model (`block+`) is more permissive than inline-only content allows (nested lists, blockquotes, code blocks, multiple paragraphs all fit `block+` but have no Markdown table-cell syntax); and `mergeCells`/`splitCell` are wired up and reachable even though a merged cell can never round-trip. Column resizing and per-cell color were never implemented in the first place, so they need no code change — only recording here as a constraint, so a future ticket doesn't reintroduce them under the assumption that their absence was an oversight rather than a deliberate limit.

## Decision

**Extend `@tiptap/extension-table`, don't replace it.** The base package's ProseMirror-level machinery — `tableEditing`'s selection/keyboard-navigation state machine, `TableMap`'s row/column bookkeeping, the existing command set — is exactly the kind of code that's cheap to get subtly wrong and expensive to verify from scratch. Since that layer was confirmed to already work, the fix is scoped to the two verified gaps rather than a rewrite.

- **Column Alignment is a cell attribute (`align: 'left' | 'center' | 'right' | null`), kept procedurally uniform per column rather than modeled as a `Table`-level array.** GFM alignment is declared once per column in the delimiter row, so it's a column-level fact — but storing it as a `Table`-level array would force every read site (rendering, future commands) through a parent-node lookup instead of reading the cell directly, and would diverge from how `marked.js` itself already reports alignment (per-cell, in its `Tokens.TableCell.align` field). The chosen shape keeps every cell self-describing while a single shared helper — `applyColumnAlign` in `table/align.ts` — is the one path allowed to *write* it, so a column's cells can never end up disagreeing about their own alignment. `Table.parseMarkdown` reads `marked.js`'s per-column `align` array and stamps it onto every cell in that column at parse time; `Table.renderMarkdown` reads it back off each column's header cell (guaranteed uniform) to pick the delimiter syntax (`:--`, `:-:`, `--:`, or plain `---`).
- **Cell content is restricted to exactly one mandatory `paragraph`** (`content: 'paragraph'`, down from `block+`). This single schema change forecloses the entire remaining fidelity gap at once: a GFM table cell is inline-only and single-line, so nested lists, blockquotes, code blocks, and additional paragraphs are all simultaneously made unrepresentable — and because it's enforced in the ProseMirror schema itself, it holds for every path that can insert content into a cell (typing, paste, programmatic commands, undo/redo), not only the ones exercised by hand.
- **`mergeCells`/`splitCell`/`mergeOrSplit` are disabled at the command layer**, overridden to no-op/return `false` on the extended `Table` node — not merely left unexposed in the UI. A merged cell has no GFM representation (`colspan`/`rowspan` don't exist in a Markdown table), so this is defense in depth: it stays impossible from any call site, including ones that don't exist yet (a future keyboard shortcut, a paste handler), rather than relying on every future call site remembering not to invoke the command.

## Alternatives considered

- **Replace `@tiptap/extension-table` (or adopt a different table library).** Rejected: the base package's parsing, serialization, and row/column command surface were verified to already work correctly; replacing it would mean re-earning correctness on ProseMirror table selection and structural editing that this package already has largely solved, in exchange for closing a gap that turned out to be much narrower than "tables are broken."
- **Store Column Alignment as a `Table`-level array indexed by column**, rather than a procedurally-uniform per-cell attribute. Rejected: adds a lookup indirection (child cell → parent Table → column index) to every alignment read for no round-trip benefit, since `marked.js` already hands alignment to the parser per-cell and the renderer already reads per-column from a representative cell either way.
- **Allow richer cell content** (e.g. `inline*` plus a single optional list, or multiple paragraphs joined by a separator on render — the latter being the base package's actual pre-existing behavior for `block+` cells). Rejected: any content richer than one paragraph either can't be represented in a single GFM table-cell line at all, or requires a lossy join/split scheme on every render/parse — the kind of "usually lossless" behavior this feature exists to eliminate, not reproduce for a different node type.

## Consequences

- A hand-authored or externally-authored Note whose table already uses column alignment now keeps that alignment through Nemos's open → edit → save cycle — the previously-silent data loss this feature exists to close.
- Pasting rich content (a list, a code block) into a table cell is silently flattened or stripped by ProseMirror's schema-fitting rather than rejected with an error, matching the editor's existing general leniency around lossy pastes elsewhere. Worth revisiting if this surfaces as a confusing "my list disappeared" support report.
- Any later ticket adding table editing commands (the handle-based UI in the parent epic) must route every alignment change through `applyColumnAlign`/`setColumnAlign` rather than setting `align` on a single cell node directly, or the column-uniformity invariant this ADR establishes silently breaks.

## Implementation pitfalls

- **Cell positions computed from a `TableMap` must be re-resolved through `tr.mapping` before each edit in the same transaction, not computed once up front.** `TableMap.positionAt(row, col, table)` returns a position in the table node as it existed *before* the transaction. `applyColumnAlign` sets `align` on every cell in a column, across every row, inside a single transaction; `setNodeMarkup` never changes a node's size, so in this specific case positions would stay technically valid even without remapping — but the helper re-resolves through `tr.mapping.map(...)` on every iteration anyway, specifically so it stays correct the moment a future command built on the same pattern (e.g. a later ticket's clear-column or sort-rows, which replace or reorder content rather than just patch attributes) does change node sizes mid-transaction. Dropping that remapping to "simplify" the loop is the trap: it would keep working for pure attribute-only edits and then silently corrupt positions the day someone reuses the pattern for a size-changing one.
